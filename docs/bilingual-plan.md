# 阿成博客中英文支持方案

状态：2026-10-27 已实现、迁移并上线。254 项自动测试、ESLint、TypeScript、OpenNext Cloudflare 构建及隔离 Worker 端到端验收通过。线上中英文页面、RSS、sitemap、访问权限和 www 跳转均已只读验收，原有 1 篇中文文章保留。

当前入口：中文 `/`，英文 `/en`，后台 `/admin/login`。线上尚无英文文章，发布英文译文后才会出现在英文列表。AI 翻译沿用后台文本模型配置；端到端测试使用固定候选文本验证预览和保存，未消耗付费供应商额度运行真实翻译。

## 1. 目标与范围

同一篇内容分别保存中文、英文两条文章记录，作者分别审核和发布，读者可以切换到对应版本。文章仍保存在现有 Cloudflare D1 数据库中，日常发布和修改文章不需要重新部署。

这一版包含：

- 后台选择文章语言、创建译文草稿、关联已有译文。
- 可选的 AI 辅助翻译，生成后先审核再发布。
- 前台中英文导航、首页、分类、搜索、文章和 RSS。
- 四套现有首页主题、移动端和公开文章的搜索引擎语言标记。
- 兼容旧文章、现有文章链接和不传语言的外部发布工具。

默认约定：中文是默认语言，管理后台继续使用中文，既有文章按中文处理；如有既有英文文章，可以在后台单独调整。手动切换语言，语言由地址决定，不按浏览器语言强制跳转。

## 2. 作者使用流程

### 2.1 发布中文与英文文章

1. 新建文章时默认选择“中文”，完成编辑后正常发布。
2. 在文章编辑页选择“新建英文译文”，系统先保存中文稿，再创建并关联一篇独立的英文草稿。
3. 可以手动写英文，也可以在这篇草稿中运行 AI 翻译。
4. 校对英文标题、摘要和正文后，单独点击发布。
5. 两个版本均符合公开条件后，读者可以在文章页切换语言。

允许先发英文再补中文，流程对称。不要求每篇文章必须有两个语言版本。

### 2.2 编辑页与文章管理

- 发布面板增加“文章语言：中文 / English”。
- 增加译文区域，显示对应版本的标题、语言和草稿/已发布状态。
- 提供“新建译文”“关联已有文章”“编辑对应版本”“解除关联”。
- 文章列表增加语言标记和“全部 / 中文 / English”筛选。
- 自动保存、草稿恢复、发布面板和重新打开编辑页都保留语言和关联关系。
- 前台管理员的行内编辑不改变语言和关联关系，需要管理译文时进入完整编辑器。
- 同一组最多一篇中文和一篇英文。重复新建时打开已有译文，不重复创建。
- 同语言文章、已经属于另一组的文章不能直接关联；明确解除旧关联后才可重绑。
- 两个版本的标题、正文、摘要、标签、发布状态、阅读量和发布时间独立维护。
- 中文原文修改后，英文稿保持原样，由作者决定何时更新译文。

### 2.3 分类与自定义导航

分类继续共用，增加可选的英文显示名称；例如“技术”在英文页面显示为“Technology”。内部分类标识不变，不创建第二套重复分类。

自定义导航增加可选英文标签。未填写英文标签时显示原标签；不在访问页面时自动调用 AI 翻译作者填写的内容。固定界面文案提供完整的中英文字典，英文站点名称默认显示为“Acheng”。

## 3. 读者体验与地址

| 页面 | 中文地址 | 英文地址 |
| --- | --- | --- |
| 首页 | `/` | `/en` |
| 文章 | `/<中文文章 slug>` | `/en/<英文文章 slug>` |
| 分类 | `/category/<slug>` | `/en/category/<slug>` |
| 搜索 | `/search?q=关键词` | `/en/search?q=keyword` |
| RSS | `/feed.xml` | `/en/feed.xml` |

- 中文原有地址保持有效；中英文文章各有独立地址。
- 保留数据库现有的 slug 全局唯一规则，创建英文草稿时可推荐 `<原 slug>-en`，发生冲突则生成其他唯一值。
- 中文首页只列中文文章，英文首页只列英文文章；分类、分页、搜索、分类计数和相关推荐使用相同语言条件。
- 顶部提供紧凑的语言切换入口；文章标题附近提供对应译文入口，沿用现有版式和主题。
- 首页切换进入另一语言首页；分类切换保留分类，搜索切换保留关键词，分页重新从第一页开始。
- 文章切换直达对应文章，不跳到无关页面。没有可公开的译文时，不提供有效的另一版本链接。
- 内部导航、搜索弹层、返回首页和 RSS 链接都保持当前语言。
- 英文的按钮、空状态、日期、阅读时间和错误提示使用英文；后台操作控件继续使用中文。
- 只有一个语言版本时可以正常发布和阅读，不展示虚假的完整双语状态。
- 中文文章的错误 `/en/...` 地址，以及英文文章的无前缀地址，统一跳转到各自规范地址，避免重复页面。

实施前检查是否存在 slug 为 `en` 的旧文章，解决新前缀与旧内容的实际冲突后再上线。

## 4. 数据与接口设计

### 4.1 文章语言和译文分组

在 `posts` 增加：

| 字段 | 含义 |
| --- | --- |
| `language` | `zh-CN` 或 `en`，非空，默认 `zh-CN` |
| `translation_group_id` | 可空的稳定分组标识，由服务端生成，同组即互为译文 |

采用分组标识而非互存 slug；修改标题或 slug 不影响关联。未关联的文章允许独立存在。

增加语言列表查询索引，以及“同组、同语言、未软删除文章唯一”的约束。分组建立、创建译文和关联操作使用数据库原子批处理，避免双击或并发创建出重复译文。

软删除保留恢复所需的关联信息，但前台立即隐藏该版本。若原位置已有新译文，恢复操作报告冲突，不自动替换现有文章；用户解除冲突后再恢复。永久删除一个版本不删除另一个版本。

分类表增加可选 `name_en`；导航沿用 `site_settings` 的 JSON 配置，扩展可选 `label_en`，兼容旧数据。

### 4.2 接口兼容与可见性

- 扩展现有创建、更新和自动保存接口的 `language` 字段；新增时缺省中文，更新时缺省保留原值，显式非法值返回校验错误。
- 译文通过鉴权接口按文章 ID 关联，服务端管理分组，不依赖文章标题猜测。
- 新建译文、关联已有译文和解除关联集中在译文管理接口，例如 `/api/admin/posts/[slug]/translations`。
- 检查源文章与目标文章存在、语言不同、未删除、未占用其他分组，并处理并发冲突。
- Obsidian 和其他发布客户端继续使用现有接口；不传新字段时保持原行为，已有英文稿更新时不会被改回中文。
- 公共列表只返回当前语言下可索引的文章；管理员列表可以查看全部语言。
- 公共译文入口、搜索引擎标记与 RSS 不泄露草稿、已删除、链接访问或密码文章的非公开信息。
- 新建译文默认草稿，并继承原文的密码/隐藏限制，防止翻译过程意外扩大访问范围。
- 译文的阅读鉴权独立执行，跳转不携带原文密码参数。

### 4.3 涉及的现有模块

- `lib/repositories/types.ts`、`posts.ts`、`categories.ts`、`search.ts`：数据类型、查询、关联和可见性。
- `app/api/posts/route.ts`、`app/api/admin/posts/[slug]/route.ts`：发布、自动保存和编辑接口。
- `app/editor/page.tsx`、`components/NovelEditor.tsx`：语言设置、译文操作和状态恢复。
- 后台文章列表、分类管理和导航管理：语言筛选及英文显示名称。
- 公共页面、`HomeClient`、四套主题、`SiteHeader`、`SiteFooter`、搜索和分页组件：传递语言和生成链接。
- `lib/related-content.ts`、`lib/background-jobs.ts`：同语言推荐及英文元数据处理。
- `middleware.ts`、`app/layout.tsx`、RSS 和 sitemap：路由语言、文档语言与搜索引擎输出。

新增共享的语言字典和 URL 辅助函数，集中维护语言代码、界面文案及地址规则。中英文页面共用现有页面组件，不复制两套业务实现。

## 5. AI 翻译设计

现有 AI 面板主要处理文本，全文上下文会在 12,000 字符处截断，默认输出长度也不适合保证整篇译文完整。因此新增“翻译为英文草稿”的流程，复用现有 AI 模型配置与调用层，而非直接用现有全文按钮保存一篇英文文章。

- 已保存的中文内容是翻译来源，目标是独立英文草稿；中文原文不受译文编辑影响。
- 翻译标题、摘要和正文，标签可由作者审核后修改；分类、封面和资源复用原记录。
- 按富文本/Markdown 结构提取文本并分块，保留标题层级、列表、表格、图片地址、链接目标、附件、代码块和嵌入内容，不把全文压成纯文本后重建。
- 受保护的代码和资源节点不交给模型改写；回填前校验节点数量、资源标识及输出完整性。
- 界面显示分段进度，支持取消；遇到超时、模型截断或格式错误时报告失败并允许重试，不把半篇结果标记为翻译完成。
- 各块完成并校验后才整体写入目标草稿，写入时校验源稿和目标稿的内容版本，避免覆盖期间的新编辑。
- 重复点击复用同一草稿；已有译文时进入编辑，重新翻译先展示候选结果，由作者主动应用，不直接覆盖。
- 初版通过可重试的分段请求完成，不新增队列服务，也不承诺关闭浏览器后继续翻译；中断时已创建草稿保留，可再次尝试。
- 模型不可用时仍可手动创建、关联和发布英文稿，清楚显示翻译失败原因。
- 自动摘要和标签生成遵循文章语言，避免英文稿发布后被后台任务回写成中文摘要；英文提示词通过语言上下文补充，保留既有自定义配置。
- AI 返回内容按不可信输入处理，限制请求长度和输出结构，不执行生成的脚本，不在客户端暴露服务端密钥。

本版不做原文修改后的自动重译，也不默认自动发布 AI 生成的内容。

## 6. 搜索引擎、缓存与兼容

- 每篇公开文章的 canonical 指向自己的语言地址；中英文使用互相对应的 `hreflang`，不把英文 canonical 指向中文。
- 公共布局在服务端输出正确的 HTML `lang`，文章 Open Graph、结构化数据和日期格式与语言一致，并验证语言切换后的文档属性。
- 站点地图包含两种语言的公开地址和有效对应关系；草稿、密码和链接访问文章继续排除。
- RSS 按语言分开输出；旧 `/feed.xml` 继续作为中文订阅地址。
- 列表、总数、分类统计、搜索和推荐均在数据库查询阶段按语言过滤，避免分页或推荐数量不一致。
- 涉及语言的查询结果和相关推荐缓存包含语言条件；发布、撤回、关联和解除关联后失效相关缓存。
- 检查数据库缓存与 Next/OpenNext 页面缓存两层，发布后主页和译文按钮都能更新，无需手动部署。
- 保留现有 `www.blog-acheng.com` 到主域名的跳转，同时验证 `/en` 路径和查询参数不会丢失。
- 上线前核实当前 D1 全文索引是否仍存在历史同步问题；如复现，针对同步问题修复并验证新增、更新和删除文章的搜索结果。

## 7. 实施顺序与验收

| 阶段 | 可交付结果 | 核心验收 |
| --- | --- | --- |
| 1. 数据与兼容 | 语言字段、分组、迁移与接口支持 | 旧文章仍能读写；旧客户端更新不清空语言；并发关联不会产生同语言重复项 |
| 2. 后台手动发布 | 选择语言、新建/关联译文、列表筛选、自动保存 | 不使用 AI 也能完成“中文发布、英文发布、后台互相打开”的完整流程 |
| 3. 前台阅读 | 英文地址、语言切换、同语言列表与字典 | 首页、分类、搜索、分页和相关推荐语言一致；无公开译文时不产生错误入口 |
| 4. AI 草稿 | 分段翻译、结构保留、失败重试、元数据语言 | 原文不变；图片代码不丢；长文不静默截断；失败不发布；已有译文不被覆盖 |
| 5. 搜索引擎与上线 | 双语 RSS、sitemap、语言标记、缓存验证 | 两种语言的规范地址和索引正确；新发布译文能在无需部署的情况下显示 |

每个阶段先通过相应的小范围测试再扩展，使用项目现有 Vitest 测试结构。整个功能完成后运行：

```bash
npm run lint
npm run test:run
npx opennextjs-cloudflare build
```

浏览器验收覆盖桌面和手机、四套主题，以及中文单篇、英文单篇、双语配对、译文草稿、译文撤回、软删除恢复、密码和链接访问。浏览器验证还包括刷新、直接打开英文链接、跨语言返回首页、搜索和修改 slug。

数据库迁移在独立本地测试数据库或隔离的预览环境验证，不用线上数据库运行破坏性测试。AI 结构与失败测试使用固定模拟响应，真实模型只做少量人工校验。

## 8. 上线、回退与成本

1. 先记录线上 D1 Time Travel 恢复点，或完成经授权的数据库备份，并确认已有表、索引、迁移记录及当前文章数量。完整本地导出需要独立的数据复制授权；本次采用 Cloudflare 自带恢复点，不复制完整数据库到本机。
2. 新增专用增量迁移，例如 `005_add_post_languages.sql`，同时更新全新安装使用的 `db/schema.sql`。根据现有迁移基线只应用尚未执行的增量，不重跑全部历史 SQL。
3. 新列默认值兼容旧代码，先应用迁移并核验，再部署已构建的新 Worker。
4. 不直接运行当前会重放完整 `db/schema.sql` 的 `npm run deploy` 脚本；使用经过验证的增量迁移和 OpenNext 部署流程，避免已有表冲突及模板设置覆盖。
5. 上线后验证中文旧文章、后台登录、英文草稿发布、双语切换、缓存更新及 www 跳转，再开放日常使用。
6. 保留前一 Worker 版本；需要回退时优先回退应用，保留新增列与已写入的译文，不通过删列或重建数据库回退。旧版本可能把英文稿混入原列表，必要时临时撤回英文稿并记录状态后再回退。

不新增域名、数据库实例、图片桶或服务器。文字存储和请求量会有所增加；中英文共用原图片资源，避免重复上传。AI 翻译费用取决于实际使用的模型、文章长度及重试次数，开始实现时不购买或升级新的服务。具体账单以账户和供应商的实际计费为准。

首次上线需要一次迁移与部署。此后正常发布、编辑、关联、解除关联中英文文章，都通过后台写入数据库，不需要再次部署。
